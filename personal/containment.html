Containment

Personal project · Unreal Engine 5.8 · 2026

23 s · 2.39:1 · ~200 MetaHumans

Role
Crowd, lighting, music sync, rendering
Engine
Unreal Engine 5.8
Tools

Year
2026

A rave inside a prison cellblock: about 200 MetaHumans packed under the catwalks, dancing to a DJ, with the lights cut to the beat. It's the third piece in the set, and the first with people in it.

The goal was a dancing crowd that reads as real on one 32 GB PC, using Unreal 5.8's new experimental MetaHuman Crowd plugin, with the final frames rendered through Movie Render Queue. Most of the work was getting an experimental tool to behave in production: finding its bugs, working around them, and staying inside a memory budget it was never sized for.

What I built

A 198-person MetaHuman crowd on the UE 5.8 MetaHuman Crowd plugin (experimental), built from 9 characters made from MetaHuman Creator presets and adjusted.
16 dance clips retargeted from Manny to the MetaHuman skeleton.
A layout script that places every dancer. No two neighbours share a dance, and the energy rises toward the DJ: calmer moves at the entry, the high-energy clips at the booth. The catwalk crowd follows the same rules.
Workarounds for the plugin's bugs (see tech notes), so faces and bodies render correctly at crowd scale.
Beat-synced lighting baked from the track at 145 BPM: 62 LED wall panels as an audio visualizer driven by a baked audio-spectrum texture (bass at the DJ end); 9 centre fluoro tubes flashing on the offbeat hi-hat as a chase that flips direction each bar; 6 moving-head beams and a DJ light strip keyed to the kick, with sweeps, a build strobe, a hit on the drop and a blackout at the end.
Seven cameras (2.39:1 angles, a 16:9 wide and a 9:16 vertical), plus empty-set and detail-lighting passes, all rendered headless with Darkroom with 0 failures.

The setup

Containment runs on one home PC: a Ryzen 7 1700, 32 GB of RAM, an RTX 5070 Ti with 16 GB, and a Windows page file that takes whatever doesn't fit in RAM.

9 characters, made from MetaHuman Creator presets and adjusted, with a mix of builds and heights.
16 dances from a Party Pack, retargeted from Manny to the MetaHuman skeleton with an IK Retargeter. All play in place and loop, and each is rated low, medium or high energy.
One Collection per dance. The crowd plugin bakes one animation per crowd type, so each dance has its own Collection with all 9 characters baked in: about 900 MB on disk each, 9 to 13 minutes per rebuild.
Instances and data assets. One instance per character in each Collection; a data asset per dance lists them, and each agent picks a character from that list.
198 single-point spawners, each with an EQS query that returns one point at the spawner. A layout script places them and assigns dances (no same-dance neighbours, energy rising toward the DJ). The 16 behind the DJ were parked when the desk went in.
A crowd sublevel, hidden with a Level Visibility track for the empty-set passes, which works in headless renders.
At render time the agents are instanced skinned meshes at low LODs. They only spawn at runtime, so Movie Render Queue warms up for 3000 frames before recording.

What it runs at

CPU vs GPU: the editor runs about 31 to 33 fps with 190 agents, with the GPU at 50 to 56%. The CPU is the limit, not the GPU; for the final frames it doesn't matter, because Movie Render Queue isn't real time.
VRAM: 11.2 GB with the 16 Collections loaded, 12.5 GB with 190 agents dancing, out of 16 GB. The crowd itself adds about 1.3 GB.
Memory (RAM plus page file): about 36 GB with the level freshly loaded. One Collection rebuild took it from about 45 to 67 GB and the editor never gave it back. The full crowd in Simulate peaks around 71 GB.
Final renders: 9 jobs of 835 frames, all on the first try, about 2 h 25 min in total, 11 to 20 minutes per camera (0.8 to 1.5 s per frame), with the whole PC peaking around 70 to 77 GB per crowd camera.

Same detail, less memory: what I'd change

One Collection, several dances. Each dance is a full copy of the same 9 characters. A Collection can bake a list of animations, so a few shared Collections could replace the 16 copies. Planned; it needs a two-dance test first, measured for build time, memory and file size.
A smaller palette per Collection. Tested: removing unused hair grooms cut a rebuild from 13.5 to 9 minutes, but memory stayed the same. Limiting each groom to the heads that wear it is what let the larger build finish. Next: cap crowd textures near 1K and drop LODs the crowd never uses.
Fewer spawners. Interleaved sub-lattices (offset grids that never share a point) would cover the same layout with about 48 spawners instead of 198. An earlier crowd version did this at 94 agents with 22 spawners. It's about a lighter scene, not memory.
Rebuild each Collection in its own process. A small C++ plugin would expose the rebuild so a batch runner can do one Collection per headless Unreal process, and the memory goes away with each process. Planned, not built: see Crowd Rebuild.
64 GB of RAM and a fixed page file on the work drive, so rebuilds stop paging. Planned.
Unload the crowd while lighting. The crowd already lives in its own sublevel; measuring the saving is next.

I'll add an old-vs-new comparison with measured results once these are done.

Today vs planned

Dance Collections: 16, one per dance → a few shared Collections with several dances each.
Collection size: about 900 MB each, around 14 GB in total → smaller, with textures capped near 1K and unused LODs dropped.
Spawners: 198, one per agent → about 48 interleaved sub-lattices.
Rebuild workflow: 1 per editor restart, by hand, 9 to 13 minutes each → a headless batch overnight, one process per Collection (about 2.5 hours for 15).
Memory after a rebuild: held until the editor restarts (about 45 → 67 GB) → released when each process exits.
Peak memory, full crowd: about 71 GB on 32 GB of RAM → target: fit in 64 GB of RAM with no paging.

Tech notes

White faces. The crowd plugin copied the editor skin settings into the crowd material, which switched off the baked face textures, so every head rendered white. The first fix patched the face materials after each build; the final crowd uses a simpler setup that doesn't need the patch.
Floating heads. One build setting merges only the visible skin into the outfit. With no top, the torso disappeared; with a top, the body took the wrong shape. Turning it off renders the real body. The crowd's garments also didn't fit the custom bodies, so the crowd stays in the MetaHuman base layer by decision. Fully dressed hero characters near the camera are a later pass.
A memory budget built around restarts. Rebuilding one crowd Collection pushed system memory commit from about 45 GB to about 67 GB on a 32 GB machine: one rebuild per editor restart, so 16 Collections meant 16 restarts. The fix for this piece was discipline: one Collection at a time, save, restart.
The crowd arriving late in the render. With a short warm-up, Movie Render Queue started recording before the crowd had fully spawned, so the first frames were half-empty. A 3000-frame warm-up gives a full crowd from frame 0.
